# Supabase и offline-first хранение — дизайн первой версии

Дата: 2026-08-11  
Статус: согласовано пользователем  
Проект: «Мои домашние дела» (Android, Kotlin, Jetpack Compose)

## Цель

Сделать данные приложения устойчивыми к закрытию, перезапуску и обновлению приложения, а затем добавить облачное хранение и синхронизацию между телефоном родителя и ребёнка. Приложение должно продолжать работать без интернета.

Удаление приложения не гарантирует сохранение только локальных данных, поэтому для восстановления после удаления используется Supabase. Android Auto Backup может рассматриваться как дополнительный механизм, но не заменяет облачную копию.

## Принятые решения

- Основная платформа остаётся Android/Kotlin; Next.js-команды `npm install` и файлы `page.tsx` не используются.
- Локальная база данных: Room.
- Фоновая синхронизация: WorkManager с ограничением `NetworkType.CONNECTED`.
- Облачный backend: Supabase Auth, Postgres и Row Level Security (RLS).
- Режим работы: offline-first. UI читает и изменяет локальные данные, а синхронизатор отправляет их при наличии сети.
- Родитель регистрируется по email и паролю.
- Ребёнок подключается к профилю по одноразовому коду приглашения.
- В первой реализации нет свободного чата с ИИ, оплаты, публикации в Google Play и расширенной аналитики.

## Компоненты

### Локальный слой

`AppRepository` остаётся границей между UI и данными. Реализация на Room содержит сущности, DAO и преобразование в доменные модели. Изменения получают локальный идентификатор, время изменения и состояние синхронизации: `PENDING`, `SYNCED` или `FAILED`.

### Supabase-клиент

Для Android используется Kotlin-клиент Supabase (не JavaScript SDK). URL и publishable key поступают через конфигурацию сборки/локальные секреты и не хранятся в исходном коде. Service role key в приложение не попадает.

### Синхронизатор

WorkManager запускает синхронизацию:

1. отправляет локальные записи со статусом `PENDING`;
2. повторяет временно неудачные операции с backoff;
3. загружает изменения, появившиеся на сервере;
4. применяет их идемпотентно по стабильному `id` и `updated_at`;
5. переводит записи в `SYNCED` или сохраняет понятную ошибку.

При конфликте изменения родителя имеют приоритет над изменением ребёнка. Для остальных конфликтов используется последнее подтверждённое изменение по `updated_at`; операции не должны создавать дубликаты звёзд или выполнений.

## Модель данных Supabase

### `families`

- `id` — UUID;
- `owner_user_id` — пользователь Supabase Auth;
- `created_at`, `updated_at`.

### `children`

- `id` — UUID;
- `family_id` — ссылка на семью;
- `display_name` — имя или псевдоним, видимый ребёнку и доступный ему для редактирования;
- `parent_label` — необязательная пометка родителя для различения детей, видимая только в кабинете родителя;
- `hero` — выбранный ребёнком дракон (`boy` или `girl`);
- `created_at`, `updated_at`.

### `chores`

- `id`, `family_id`, `child_id`;
- `title`, `is_required`, `difficulty`, `schedule`;
- `created_at`, `updated_at`, `archived_at`.

### `chore_completions`

- `id`, `chore_id`, `child_id`;
- `completion_date`, `status`, `confirmed_by_parent`;
- `created_at`, `updated_at`.

Уникальный индекс `(chore_id, completion_date)` не позволяет повторно начислить выполнение за тот же день.

### `rewards`

- `id`, `child_id`;
- `stars`, `game_progress`, `unlocked_items`;
- `created_at`, `updated_at`.

Изменения наград должны быть транзакционными и повторяемыми без двойного начисления.

### `invite_codes`

- `id`, `family_id`, `child_id`;
- хранится хэш кода, а не сам код;
- `expires_at`, `used_at`, `created_at`.

Код одноразовый, имеет срок действия и после использования не принимается повторно.

## Авторизация и безопасность

- Родитель входит через Supabase Auth по email и паролю.
- RLS разрешает родителю читать и изменять только собственную семью и её профили. `parent_label` никогда не отдаётся в детскую сессию.
- После подключения устройства ребёнка его сессия ограничивается назначенным `child_id`.
- Ребёнок не может получить список других семей или детей.
- Publishable key допустим в Android-клиенте только вместе с корректными RLS-политиками; service role key запрещён.
- Код приглашения не передаётся в открытых логах и после использования аннулируется.

## Пользовательские потоки

### Родитель

1. Регистрируется или входит в аккаунт.
2. Создаёт профиль ребёнка и задаёт начальное имя/псевдоним.
3. При необходимости добавляет отдельную родительскую пометку, например «Маша старшая». Эта пометка нужна только родителю и не показывается ребёнку.
4. Получает одноразовый код подключения.
5. Настраивает дела, награды и подтверждения.
6. Видит состояние синхронизации.

### Ребёнок

1. Вводит код приглашения на своём телефоне.
2. При необходимости редактирует своё отображаемое имя.
3. Сам выбирает дракона; родитель не выбирает его вместо ребёнка.
4. Выполняет дела без интернета.
5. После появления сети изменения отправляются родителю.

### Отмена действий

- Ребёнок может отменить ошибочную отметку выполнения дела в течение текущего дня до окончательного подтверждения родителем.
- Родитель может отменить отметку ребёнка, подтверждение или собственное изменение дела из кабинета родителя.
- При отмене запись выполнения получает статус `CANCELLED`, а начисленные за неё звёзды и прогресс игры пересчитываются идемпотентно.
- Отмена требует явного подтверждения и попадает в историю изменений, чтобы синхронизация не создала выполнение повторно.

## Этапы реализации

1. Подключить Room и описать локальные сущности/DAO.
2. Перевести `AppRepository` с временного состояния на Room.
3. Добавить восстановление локального состояния после перезапуска.
4. Подключить Supabase Auth для родителя.
5. Создать таблицы, индексы и RLS-политики Supabase.
6. Реализовать создание и одноразовое использование invite-кода.
7. Добавить отмену выполнения дел и пересчёт наград.
8. Добавить WorkManager и outbox-синхронизацию.
9. Добавить отображение статуса сети/синхронизации.
10. Проверить повторные попытки, конфликты и обновление APK.

## Критерии готовности

- После закрытия и повторного запуска дела, имена, драконы, звёзды и прогресс сохраняются.
- Основные сценарии работают без подключения к интернету.
- После восстановления сети изменения синхронизируются автоматически.
- Установка обновления APK не стирает локальные данные.
- После удаления и повторной установки данные восстанавливаются после входа родителя в Supabase.
- Код приглашения нельзя использовать дважды или после истечения срока.
- Ребёнок может отменить ошибочную отметку, а родитель — отменить её или другое изменение с корректным пересчётом наград.
- RLS не позволяет одной семье читать данные другой.
- Повторная синхронизация не создаёт дубликаты дел, выполнений и звёзд.
- `assembleDevDebug`, unit-тесты и базовые UI-тесты проходят успешно.
